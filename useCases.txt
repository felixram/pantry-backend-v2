TECHNOLOGY STACK:
-----------------
- API Framework: tRPC (Type-safe RPC framework)
- HTTP Server: Express.js
- Database: PostgreSQL
- ORM: Drizzle ORM
- Language: TypeScript
- Validation: Zod schemas
- Authentication: JWT (JSON Web Tokens)
- Testing: Vitest

ARCHITECTURE PATTERN:
--------------------
- Type-safe API using tRPC (not traditional REST)
- Domain-driven design with controllers organized by business domain
- Transaction-safe operations using Drizzle ORM
- Role-based access control (ADMIN/USER)
- Comprehensive audit trails for critical operations

API ENDPOINT FORMAT:
-------------------
All API calls use the tRPC format:
POST http://localhost:3030/trpc/<router>.<procedure>

Example: POST http://localhost:3030/trpc/product.create

TOTAL ENDPOINTS: 50 procedures across 10 routers

2. AUTHENTICATION & AUTHORIZATION USE CASES
================================================================================

UC-AUTH-001: User Login
------------------------
Actor: Any user
Description: Authenticate user credentials and establish session
Input: email, password
Process:
  1. Validate user exists in database
  2. Check user status is ACTIVE (not INACTIVE)
  3. Compare password hash using bcrypt
  4. Generate JWT token with 7-day expiration
  5. Set HTTP-only secure cookie
Output: User information and authentication token
Endpoint: auth.login
Access: Public

UC-AUTH-002: User Logout
-------------------------
Actor: Authenticated user
Description: Terminate user session
Process:
  1. Clear authentication cookie (sets expiration to epoch)
  2. Invalidate session
Output: Success confirmation message
Endpoint: auth.logout
Access: Authenticated
Procedure Type: mutation (requires user session)

UC-AUTH-003: Get Current User
------------------------------
Actor: Authenticated user
Description: Retrieve current user information from session
Process:
  1. Extract JWT from cookie
  2. Verify token signature and expiration
  3. Return user details
Output: Current user information (id, name, email, role)
Endpoint: auth.current
Access: Authenticated

AUTHORIZATION LEVELS:
--------------------
1. Public: No authentication required (login, initial user creation)
2. Authenticated: Valid user session required (most operations)
3. Admin: Requires ADMIN role (location management, admin user updates)

USER ROLES:
----------
- ADMIN: Full system access, can manage locations and all users
- USER: Standard access to inventory operations

USER STATUS:
-----------
- ACTIVE: User can login and perform operations
- INACTIVE: User account disabled, cannot login

UC-PROD-001: Create Product
----------------------------
Actor: Authenticated user
Description: Create new product with initial version
Input:
  - name (required)
  - sku (optional, must be unique)
  - unit (required, e.g., "kg", "unit", "liter")
  - costPrice (optional)
  - sellingPrice (optional)
  - description (optional)
  - supplier_id (optional)
  - category_id (optional)
Process:
  1. Validate SKU is unique (if provided)
  2. Create Product record in transaction
  3. Create ProductVersion record (version 1)
  4. Update Product.activeVersionId to link to version
  5. Return product and version IDs
Output: Product ID, Version ID, success message
Endpoint: product.create
Access: Authenticated
Business Rule: SKU must be unique across all products

UC-PROD-002: Update Product
----------------------------
Actor: Authenticated user
Description: Update product details, creates new version if price changes
Input:
  - id (required)
  - name, sku, unit, supplier_id, category_id (optional)
  - costPrice, sellingPrice, description (optional)
Process:
  1. Validate product exists
  2. Check if costPrice or description changed
  3. If changed: Create new ProductVersion with incremented versionNumber
  4. Update Product record
  5. If new version created, update activeVersionId
Output: Success message, new version number (if created)
Endpoint: product.update
Access: Authenticated
Business Rule: Price changes trigger new version creation

UC-PROD-003: Get All Products

---------------------------------------

PRODUCT VERSIONING SYSTEM:
--------------------------
Every product maintains a version history:
- Version 1 created with initial product
- New version created when costPrice or description changes
- Each version has: versionNumber, costPrice, sellingPrice, description, createdAt
- Product.activeVersionId points to current version
- Enables historical price tracking and cost analysis

UC-STOCK-004: Adjust Stock Quantity
------------------------------------
Actor: Authenticated user
Description: Increase or decrease stock quantity
Input:
  - stock_id (required)
  - change_qty (required, positive=increase, negative=decrease)
  - reason (required, min 3 characters)
Process:
  1. Validate stock record exists
  2. Calculate new quantity (current + change_qty)
  3. Validate new quantity >= 0 (no negative stock)
  4. Update stock quantity in transaction
  5. Log stock movement with user_id and reason
Output: New quantity, success message
Endpoint: stock.adjust
Access: Authenticated
Business Rule: Stock quantity cannot go negative

UC-STOCK-005: Transfer Stock Between Locations
-----------------------------------------------
Actor: Admin user
Description: Move stock from one location to another
Input:
  - product_id (required)
  - from_location_id (required)
  - to_location_id (required)
  - qty (required, must be positive)
  - reason (required, min 3 characters)
Process:
  1. Validate locations are different
  2. Find or create stock records at both locations
  3. Validate sufficient stock at source (qty available >= qty to transfer)
  4. In transaction:
     a. Decrease source location stock
     b. Increase destination location stock (create if doesn't exist)
     c. Log negative movement at source
     d. Log positive movement at destination
     e. Cross-reference movements in reason field
Output: Success confirmation with movement details
Endpoint: stock.transfer
Access: Admin Only
Business Rules:
  - Cannot transfer to same location
  - Must have sufficient stock at source
  - Both movements logged for audit trail

UC-STOCK-006: Set Minimum Stock Level

Process:
  1. Validate stock record exists
  2. Update minimum stock level
Output: Success confirmation
Endpoint: stock.setMinimumLevel
Access: Admin Only
Purpose: Enables low stock alerts and automatic reorder suggestions

UC-PO-001: Create Purchase Order
---------------------------------
Actor: Authenticated user
Description: Create or update draft purchase order
Input:
  - supplier_id (required)
  - destination_location_id (optional)
  - items (array, each with product_id, qty, unit_price)
  - purchase_order_id (optional, for updating existing draft)
Process:
  1. Validate supplier exists
  2. If purchase_order_id provided:
     a. Validate PO exists and is in DRAFT status
     b. Delete existing items
     c. Create new items
  3. If new PO:
     a. Create PurchaseOrder with DRAFT status
     b. Create PurchaseOrderItems
Output: Purchase order ID and items
Endpoint: purchaseOrder.create
Access: Authenticated
Business Rule: Can only modify DRAFT status orders

UC-PO-002: Update Purchase Order Status
----------------------------------------
Actor: Authenticated user
Description: Update PO status through workflow state machine
Input:
  - purchase_order_id (required)
  - status (required)
  - destination_location_id (optional, required for RECEIVED status)
  - reason (optional, for audit log)
Process:
  1. Validate PO exists
  2. Validate status transition is allowed (state machine)
  3. If status = RECEIVED:
     a. Validate destination_location_id provided
     b. Process received items (update stock levels)
     c. Log stock movements
  4. Update PO status in transaction
  5. Log change to audit table
Output: Success message, updated PO
Endpoint: purchaseOrder.update
Access: Authenticated

PURCHASE ORDER STATE MACHINE:
-----------------------------
DRAFT → PENDING_APPROVAL → APPROVED → ORDERED → RECEIVED
  ↓           ↓              ↓          ↓
CANCELLED  REJECTED      CANCELLED  CANCELLED

Terminal States (no further updates allowed):
- RECEIVED
- REJECTED
- CANCELLED

Valid Transitions:
- DRAFT → PENDING_APPROVAL, CANCELLED
- PENDING_APPROVAL → APPROVED, REJECTED, CANCELLED
- APPROVED → ORDERED, CANCELLED
- ORDERED → RECEIVED, CANCELLED

UC-PO-007: Add Item to Purchase Order
--------------------------------------
Actor: Authenticated user
Description: Add a new line item to an existing purchase order
Input:
  - purchaseOrderId (required)
  - product_id (required)
  - qty (required, positive)
  - unit_price (required, non-negative)
  - reason (required, minimum 3 characters)
Process:
  1. Validate PO exists and is not in terminal state (RECEIVED, REJECTED, CANCELLED)
  2. Validate product exists
  3. Create new PurchaseOrderItem
  4. If PO status is PENDING_APPROVAL, APPROVED, or ORDERED and user is not ADMIN:
     a. Auto-revert PO status to DRAFT
     b. Log audit entry with change reason
  5. Log audit entry for item addition
Output: New item ID, success message
Endpoint: purchaseOrder.addItem
Access: Authenticated
Business Rule: Adding items to non-draft POs reverts them to DRAFT if user is not admin

UC-PO-008: Update Purchase Order Item
--------------------------------------
Actor: Authenticated user
Description: Modify quantity and/or price of a line item
Input:
  - purchaseOrderId (required)
  - itemId (required)
  - qty (optional, positive)
  - unit_price (optional, non-negative)
  - reason (required, minimum 3 characters)
Process:
  1. Validate PO and item exist
  2. Validate PO is not in terminal state
  3. Store old values for audit
  4. Update item with new values
  5. If PO status is PENDING_APPROVAL, APPROVED, or ORDERED and user is not ADMIN:
     a. Auto-revert PO status to DRAFT
     b. Log audit entry
  6. Log item update to audit trail
Output: Updated item, success message
Endpoint: purchaseOrder.updateItem
Access: Authenticated
Business Rule: Item updates to non-draft POs revert them to DRAFT if user is not admin

UC-PO-009: Remove Item from Purchase Order
-------------------------------------------
Actor: Authenticated user
Description: Delete a line item from a purchase order
Input:
  - purchaseOrderId (required)
  - itemId (required)
  - reason (required, minimum 3 characters)
Process:
  1. Validate PO and item exist
  2. Validate PO is not in terminal state
  3. Delete item from database
  4. If PO status is PENDING_APPROVAL, APPROVED, or ORDERED and user is not ADMIN:
     a. Auto-revert PO status to DRAFT
     b. Log audit entry
  5. Log item removal to audit trail
Output: Success message
Endpoint: purchaseOrder.removeItem
Access: Authenticated
Business Rule: Item deletion from non-draft POs reverts them to DRAFT if user is not admin

PURCHASE ORDER NUMBERING SYSTEM:
--------------------------------
- Auto-generated PO numbers with format: PO-YYYY-XXX
  - YYYY: 4-digit year
  - XXX: 3-digit sequential number (restarts each year)
- Examples: PO-2026-001, PO-2026-002, ..., PO-2026-999
- Generated on first purchase order creation of each year
- Tracked in po_counter table with fields:
  - id: unique identifier
  - year: year of counter
  - last_sequence: last used sequence number
  - createdAt, updatedAt: timestamps

PURCHASE ORDER AUDIT TRAIL:
---------------------------
Every change to a purchase order is logged:
- Field: Which field was changed
- Old Value: Previous value
- New Value: New value
- User: Who made the change
- Reason: Why the change was made
- Timestamp: When the change occurred

UC-RPT-001: Low Stock Report
-----------------------------
Actor: Authenticated user
Description: Identify products below minimum stock levels
Process:
  1. Query all stock records
  2. Filter where qty < minimumStockLevel
  3. Calculate shortage (minimumStockLevel - current qty)
  4. Include product and location details
  5. Order by shortage (largest first)
Output:
  - Product name and ID
  - Location name
  - Current quantity
  - Minimum level
  - Shortage amount
Endpoint: report.lowStock
Access: Authenticated
Purpose: Identify reorder needs

  1. Query all suppliers with purchase orders
  2. For each supplier calculate:
     - Total orders placed
     - Orders by status (completed, cancelled, etc.)
     - Total order value
     - Average order value
     - Completion rate (%)
  3. Order by total orders or value
Output:
  - Supplier name

  - Performance indicators
Endpoint: report.supplierPerformance

12. TECHNICAL USE CASES
================================================================================

UC-TECH-001: Database Transactions
-----------------------------------
Description: Ensure data consistency across related operations
Implementation:
  - All critical operations use Drizzle ORM transactions
  - Atomic operations (all succeed or all fail)
Examples:
  - Product creation (Product + ProductVersion)
  - Stock transfer (source decrease + destination increase + 2 movements)
  - PO receiving (PO update + stock updates + movement logging)

UC-TECH-002: Audit Trail Logging
---------------------------------
Description: Track all changes for compliance and debugging
Implementation:
  - StockMovement table: logs all inventory changes
  - PurchaseOrderAudit table: logs all PO field changes
  - User tracking: all movements include user_id
  - Reason tracking: all changes require reason field

UC-TECH-003: Soft Delete Pattern
---------------------------------
Description: Preserve historical data while removing from active use
Implementation:
  - Most entities have deletedAt timestamp field
  - Locations have deletedBy user reference
  - Queries filter out deleted records by default
Entities with soft delete:
  - Users
  - Locations
  - Suppliers
  - Products
  - Purchase Orders

UC-TECH-004: Product Versioning
--------------------------------
Description: Track historical product data and price changes
Implementation:
  - ProductVersion table with versionNumber
  - New version created on price/description change
  - Product.activeVersionId points to current version
  - All versions preserved for historical analysis
Benefits:
  - Price history tracking
  - Cost trend analysis
  - Historical reporting accuracy

UC-TECH-005: Type Safety
-------------------------
Description: Prevent runtime errors through compile-time checking
Implementation:
  - TypeScript throughout codebase
  - tRPC for type-safe API contracts
  - Zod schemas for runtime validation
  - Drizzle ORM for type-safe database queries

UC-TECH-006: Role-Based Access Control
---------------------------------------
Description: Restrict operations based on user role
Implementation:
  - Three procedure types: public, authedProcedure, adminProcedure
  - Middleware checks user role before execution
  - UNAUTHORIZED error if not authenticated

UC-TECH-007: Security Hardening

CORE TABLES (12):
----------------

1. users
   - User accounts with authentication
   - Fields: id, name, lastName, email, password, role, status
   - Roles: ADMIN, USER
   - Status: ACTIVE, INACTIVE

2. category
   - Product categories
   - Fields: id, name (unique), description

3. location
   - Warehouse/storage locations
   - Fields: id, name, address, city, state, country, latitude, longitude
   - Supports soft delete with deletedBy user reference

4. supplier
   - Supplier information
   - Fields: id, name, contact_name, phone, email, delivery_days,
             free_shipping_minimum, supplier_type

5. product
   - Base product information
   - Fields: id, sku (unique), name, unit (array), category_id, supplier_id,
             activeVersionId
   - Relations: belongs to Category, Supplier; has many ProductVersions

6. product_version
   - Product pricing and description history
   - Fields: id, productId, versionNumber, costPrice, sellingPrice, description
   - Relations: belongs to Product
   - Purpose: Historical tracking

7. stock
   - Current inventory levels
   - Fields: id, location_id, productId, qty, minimumStockLevel
   - Unique constraint: (location_id, productId)
   - Relations: belongs to Location and Product

8. stock_movement
   - Inventory change audit log
   - Fields: id, product_id, location_id, change_qty, reason, user_id
   - Relations: belongs to User, Location, Product

9. purchase_order
   - Purchase orders
   - Fields: id, supplier_id, destination_location_id, status
   - Status: DRAFT, PENDING_APPROVAL, APPROVED, ORDERED, RECEIVED,
             REJECTED, CANCELLED
   - Relations: belongs to Supplier, Location; has many PurchaseOrderItems

10. purchase_order_item
    - Line items in purchase orders
    - Fields: id, purchase_order_id, product_id, qty, unit_price
    - Relations: belongs to PurchaseOrder and Product

11. purchase_order_audit_log
    - PO change audit trail
    - Fields: id, purchaseOrderId, userId, fieldChanged, oldValue,
              newValue, reason
    - Relations: belongs to PurchaseOrder and User

12. po_counter
    - Sequential PO number generator (per year)
    - Fields: id, year, last_sequence, createdAt, updatedAt
    - Purpose: Generates unique PO numbers in format PO-YYYY-XXX
    - Incremented automatically when new PO created each year

RELATIONSHIPS:
-------------
Product → ProductVersion (one-to-many, cascade delete)
Product → Category (many-to-one, set null on delete)
Product → Supplier (many-to-one, set null on delete)
Location → Stock (one-to-many, cascade delete)

PurchaseOrder → Location (many-to-one)
PurchaseOrder → PurchaseOrderItem (one-to-many, cascade delete)
User → StockMovement (one-to-many, set null on delete)

15. BUSINESS WORKFLOWS
================================================================================

WORKFLOW 1: Product Lifecycle
------------------------------
1. Create product with initial version (version 1)
2. Product used in inventory operations
3. Update product price → creates version 2
4. Historical analysis uses all versions
5. Soft delete when no longer needed

WORKFLOW 2: Inventory Receiving
--------------------------------
1. Create purchase order (DRAFT status)
2. Add items to PO
3. Submit for approval (PENDING_APPROVAL)
4. Approve PO (APPROVED status)
5. Send to supplier (ORDERED status)
6. Receive shipment:
   a. Update PO status to RECEIVED
   b. Automatically update stock levels at destination
   c. Log stock movements for audit
   d. Create stock records if don't exist

WORKFLOW 3: Stock Transfer
---------------------------
1. Select product and source location
2. Specify destination and quantity
3. System validates sufficient stock
4. Transaction:
   a. Decrease source stock
   b. Increase destination stock
   c. Log both movements
   d. Cross-reference in reasons
5. Audit trail preserved

WORKFLOW 4: Reorder Process
----------------------------
1. Run low stock report
2. Identify items below minimum
3. Create purchase order for needed items
4. Follow PO workflow (above)
5. Receive and restock

WORKFLOW 5: User Onboarding
----------------------------
1. First user creates account (auto-ADMIN)
2. Admin creates additional users
3. Users login with credentials
4. JWT token stored in secure cookie
5. Token validates on each request
6. Users perform role-appropriate operations

WORKFLOW 6: Cost Analysis
--------------------------
1. Product created with initial cost
2. Cost updated over time (creates versions)
3. Purchase orders record actual purchase costs
4. Run cost analysis:
   a. Calculate average from versions
   b. Get last actual purchase cost
   c. Identify price trends
   d. Compare historical data
5. Use for pricing decisions

BUSINESS RULES SUMMARY
================================================================================

1. SKUs must be unique across all products
2. Stock quantities cannot be negative
3. One stock record per product-location pair
4. Purchase orders follow strict state machine (no invalid transitions)
5. Terminal PO states (RECEIVED, REJECTED, CANCELLED) cannot be modified
6. Product price changes trigger new version creation
7. First user automatically becomes ADMIN
8. Stock transfers require reason (minimum 3 characters)
9. All stock movements logged with user and reason
10. Receiving PO requires destination location
11. Category names are unique (case-insensitive)
12. Soft deletes preserve historical data
13. Only ACTIVE users can login
14. Admin role required for location management
15. Users can only update their own profile (unless admin)
16. PO numbers auto-generated in format PO-YYYY-XXX (unique per year)
17. Adding/updating/removing items requires reason field (min 3 chars)
18. Adding items to approved/ordered POs reverts them to DRAFT (user role only)
19. All PO item changes require audit trail logging
20. Supplier getAll supports pagination with limit/offset parameters
21. Passwords must be 8+ characters with uppercase, lowercase, and number
22. Rate limiting: 100 requests/15min general, 10 login attempts/15min
23. Health endpoints must remain accessible for orchestration

SECURITY FEATURES
================================================================================

1. JWT Authentication
   - 7-day token expiration
   - HTTP-only secure cookies
   - Signed tokens with secret key

2. Password Security
   - Bcrypt hashing with 10 salt rounds
   - Passwords never stored in plain text
   - Strong validation: 8+ characters, uppercase, lowercase, number required

3. Role-Based Access Control
   - Three authorization levels (public, authenticated, admin)
   - Middleware enforcement at API layer

4. Input Validation
   - Zod schemas validate all inputs
   - Type checking prevents injection attacks

5. Audit Trails
   - All critical changes logged
   - User attribution on all modifications

6. HTTP Security Headers (Helmet.js)
   - X-Content-Type-Options: nosniff
   - X-Frame-Options: DENY (clickjacking protection)
   - X-XSS-Protection: enabled
   - Content-Security-Policy: configured
   - Strict-Transport-Security: enabled (HTTPS enforcement)

7. Rate Limiting
   - General: 100 requests per 15 minutes per IP
   - Login: 10 attempts per 15 minutes per IP
   - HTTP 429 response when exceeded

8. CORS Configuration
   - Environment-driven allowed origins (ALLOWED_ORIGINS)
   - Credentials enabled for cookie-based auth
   - Strict origin validation

9. Cookie Security
   - httpOnly: true (prevents XSS access)
   - secure: true (production, HTTPS only)
   - sameSite: strict (CSRF protection)

10. Error Sanitization
    - Internal errors hidden from clients
    - Proper TRPCError codes returned
    - No stack traces in production
